# sitesnap v0.2.1 — Japanese Localization + `--version` + HTML Detection

**Goal:** Ship a polished v0.2.1 that publishes to npm cleanly. Add a `--version` flag, detect when users pass an HTML URL to `site` (instead of a sitemap), and translate all user-facing English text to Japanese to match the new Japanese-default README.

**Out of scope:** Login/auth support, demo GIF (deferred to v0.3 polish), `--allow-html-as-sitemap` strict-parse override, locale-detection (single-locale Japanese is sufficient for v0.2.1).

**Compatibility:** No API breaks. Output structure (`meta.json`, file paths) unchanged. Existing scripts that grep stdout for English keywords like "Done:" or "ok" will break — flagged in CHANGELOG as a non-API behavior change.

---

## Features

### A. `--version` / `-v` flag

**Behavior**
```
$ sitesnap --version
0.2.1
$ sitesnap -v
0.2.1
```

**Implementation**
- `cli.mjs` argv parser: check for `--version` or `-v` before subcommand dispatch.
- Print the `VERSION` constant from `src/config.mjs`.
- Exit 0.
- HELP table gains one line: `sitesnap --version           バージョン番号を表示`

**Edge cases**
- `--version` overrides any other args (`sitesnap site x.xml --version` still prints version and exits).
- No conflict with existing flags: `-v` is currently unused; `--version` is unused.

### B. HTML-as-sitemap detection

**Behavior**
```
$ sitesnap site https://tsukurikae.jp/
sitemapを展開中: https://tsukurikae.jp/
Error: URLがHTMLを返しました（sitemapではありません）: https://tsukurikae.jp/
ヒント: 単一ページなら 'sitesnap page <url>' を使うか、
実際のsitemap位置を確認してください（/sitemap.xml や /robots.txt 内）。
```

**Implementation**
- In `src/sitemap.mjs` `fetchXml`, after `fetch` returns ok:
  ```js
  const ct = res.headers.get('content-type') || '';
  if (/text\/html/i.test(ct)) {
    throw new Error(
      `URLがHTMLを返しました（sitemapではありません）: ${url}\n` +
      `ヒント: 単一ページなら 'sitesnap page <url>' を使うか、\n` +
      `実際のsitemap位置を確認してください（/sitemap.xml や /robots.txt 内）。`
    );
  }
  ```
- Check happens before XML parsing, so fast-xml-parser never sees the HTML.

**Edge cases**
- Servers that misconfigure Content-Type (e.g., serve real XML as `text/html`): user gets the friendly error and can investigate; no silent failure.
- Servers that omit Content-Type: fall through to XML parsing; if that fails, the original (less friendly) parse error appears. Acceptable — most servers set Content-Type.

**Stays English (deliberate)**
- Worker progress format: `[desktop] 1/3 ok URL` and `[mobile] 1/3 ERR URL :: error message` — 3-letter status codes (`ok`, `ERR`, `skip`) are scannable at a glance, especially with many URLs flying by.
- HELP examples (literal shell commands users type).
- Flag names (`--limit`, `--strict`, etc.).
- Subcommand names (`site`, `page`, `list`, etc.).
- Internal exception messages from Node / Playwright / fast-xml-parser (we don't translate library output).

## CHANGELOG entry

```markdown
## [0.2.1] - 2026-05-04

### Added
- `--version` / `-v` flag: print the installed version and exit.
- Friendly Japanese error when `site` is given an HTML URL instead of a sitemap; suggests using `page` or checking `/robots.txt` for the actual sitemap path.

### Changed
- All user-facing CLI text (errors, help, progress messages) is now in Japanese to match the Japanese-default README. Worker progress lines (`[desktop] 1/3 ok URL`) keep the English status codes for at-a-glance readability.

### Notes for downstream scripts
This release changes log/error string formats. Scripts that grep for English keywords like "Done:", "Found", or "Refusing to fetch" need to update to the Japanese equivalents (or use `--json` for stable structured output, which is unaffected).
```

1. Implement per the writing-plans output.
2. `npm test` — all tests pass.
3. Manual smoke: `node cli.mjs --version`, `node cli.mjs help`, `node cli.mjs site <html-url>` (verify friendly error).
4. Bump `package.json` version 0.2.0 → 0.2.1.
5. Add 0.2.1 entry to CHANGELOG.
6. Commit, tag, push.
7. `npm publish --access public`.
8. Verify on npmjs.com that the page renders Japanese README.

## Open questions / decisions made

- **Q: Should HELP examples be translated?** A: No — they're literal shell commands. Translating example text would make them broken commands.
- **Q: Should `[desktop] 1/3 ok` be Japanese?** A: No — kept English for visual scanning when 100+ URLs are processed. The text-heavy lines (`Done: ...`, errors, hints) are translated.
- **Q: Should we add a `--lang en` opt-out?** A: No — YAGNI. If demand exists post-publish, add in v0.3.
- **Q: Should top-level `Error: ${e.message}` translate the inner message?** A: No — `e.message` may come from libraries (Playwright, fast-xml-parser, fetch) and translating those is out of scope. Only sitesnap's own throws are translated.
